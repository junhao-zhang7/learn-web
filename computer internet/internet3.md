1. PID:操作系统为每个正在运行的进程（程序）分配的唯一数字编号，用于区分和管理不同的程序案例
2. TCP三次握手：
   TCP 三次握手（Three-Way Handshake） 是 TCP 协议建立可靠连接的核心过程。为了让你彻底理解，我们从目的、具体步骤、核心报文标志位、通俗类比四个维度进行拆解。
 
 
 
一、 核心目的
 
在客户端和服务器之间建立全双工的通信通道，并同步双方的序列号（Sequence Number），确保双方都具备收发数据的能力。
 
二、 详细步骤拆解（带标志位与序列号）
 
TCP 报文头部有两个关键标志位参与此过程：
 
- SYN (Synchronize)：同步序列号，用于发起连接。
- ACK (Acknowledgment)：确认号，用于确认收到数据。
 
第 1 次握手：客户端 → 服务器（发起请求）
 
- 动作：客户端向服务器发送一个SYN 报文。
- 关键信息：
- 标志位： SYN = 1 
- 序列号： seq = x （客户端随机生成的初始序列号，记为 ISN_C）。
- 状态变化：客户端进入  SYN_SENT  状态，等待服务器确认。
 
第 2 次握手：服务器 → 客户端（确认+同步）
 
- 动作：服务器收到 SYN 后，回复一个SYN + ACK 报文。这是“二次握手”的关键，包含两层意思：
1. ACK：告诉客户端“我收到了你的连接请求”。
2. SYN：告诉客户端“我也想和你建立连接，请确认我的序列号”。
- 关键信息：
- 标志位： SYN = 1, ACK = 1 
- 确认号： ack = x + 1 （期望收到的下一个字节是 x+1）。
- 序列号： seq = y （服务器随机生成的初始序列号，记为 ISN_S）。
- 状态变化：服务器进入  SYN_RCVD  状态。
 
第 3 次握手：客户端 → 服务器（最终确认）
 
- 动作：客户端收到 SYN+ACK 后，回复一个ACK 报文。
- 关键信息：
- 标志位： ACK = 1 
- 确认号： ack = y + 1 （告诉服务器“我收到了你的同步，准备好通信了”）。
- 序列号： seq = x + 1 。
- 状态变化：
- 客户端发送后，进入  ESTABLISHED （已建立）状态。
- 服务器收到后，也进入  ESTABLISHED  状态。
- 此时，连接正式建立，双方可以开始传输数据。
 
 
 
三、 为什么需要“三次”而不是“两次”？
 
这是面试和考试中的高频问题，核心原因是防止“失效的连接请求报文段”被误处理。
 
1. 场景假设：客户端发送的第一个 SYN 报文因为网络拥堵延迟了，客户端超时重连并建立了正常连接，传输完数据后断开。
2. 问题出现：过了很久，那个延迟的“旧 SYN 报文”突然到达了服务器。
3. 两次握手的后果：服务器会认为这是一个新的请求，直接建立连接并等待数据。但客户端其实没有发起请求，不会发送数据，导致服务器资源被浪费（半开连接）。
4. 三次握手的作用：服务器收到“旧 SYN”并回复 SYN+ACK 后，客户端发现自己没有对应的请求，会丢弃该报文，不发送第三次 ACK。服务器收不到 ACK，就会超时关闭这个无效连接，从而避免资源浪费。
 
四、 通俗类比（打电话）
 
为了确保通话双方都能听见且听清楚：
 
1. 客户端（你）：喂，能听到吗？（SYN，发起请求）
2. 服务器（我）：能听到，你能听到我吗？（SYN+ACK，确认收到 + 反问）
3. 客户端（你）：能听到，我们开始聊吧。（ACK，最终确认，通话开始）
 
 
 
五、 常见面试/笔试考点
 
1. 半连接队列：服务器处于  SYN_RCVD  状态的连接会被放入半连接队列，第三次握手成功后才会移到全连接队列。
2. SYN 泛洪攻击：攻击者发送大量 SYN 报文但不回复第三次 ACK，占满服务器半连接队列，导致正常连接无法建立。
3. ISN 是随机的：初始序列号不是从 0 开始，而是随机生成的，目的是为了安全性，防止被猜测序列号进行攻击。
3. ARP:地址解析协议，是IPv4网络中跨网络层与数据链路层的核心协议，核心作用是将目标IP地址解析为对应的MAC地址
4. 五层TCP/IP模型
1- 应用层：介质：client:浏览器/微信 CS架构（client and sever）
         app或浏览器使用特定的应用层协议如http(80),https(443),DNS(53)等按照协议的方式把数据进行封装，生成数据包，核心作用：将数据转换为网络可传输的标准格式
2- 传输层：介质：OS，使用UDP/TCP协议封装数据，包含源端口和目标端口，通过端口区分应用，准确送达对应应用程序
3- 网络层：介质：路由器，确定发到哪台设备，封装IP协议，包含源IP和目标IP
4- 数据链路层：介质：WiFi AP/交换机/网卡，主机发送APR请求帧，询问网关mac地址，封装成数据帧（frame）包含源mac地址和目标mac地址，定位目标设备的局域网 
5- 物理层：介质：光纤，数字信号转换为物理信号
数据帧：源mac地址，源IP，源端口，data，目标端口，目标IP，目标mac地址
5. 以 Windows 系统请求百度 IP（ www.baidu.com ） 为例，结合你之前学的 端口、ARP、Frame 知识，我们按照 TCP/IP 五层模型（应用层、传输层、网络层、数据链路层、物理层）进行全流程拆解。
 
 
 
场景设定
 
- 客户端：Windows 10/11 (IP: 192.168.1.100)
- DNS 服务器：公共 DNS (如 223.5.5.5 阿里云 DNS)
- 目标：获取  www.baidu.com  的 IP 地址。
- 核心协议：DNS (基于 UDP)、ARP、IP、Ethernet。
 
 
 
第一层：应用层（Application Layer）
 
动作：发起请求
 
1. 触发：你在浏览器输入  www.baidu.com  并回车。
2. 解析请求：浏览器调用操作系统的解析器（Resolver），请求将域名转换为 IP。
3. 递归查询：系统检查本地  hosts  文件和 DNS 缓存，若未命中，则向配置好的 DNS 服务器（223.5.5.5） 发起请求。
4. 数据：生成 DNS 查询报文（包含要查询的域名  www.baidu.com ）。
 
 
 
第二层：传输层（Transport Layer）
 
动作：添加端口，实现进程寻址
 
1. 协议选择：DNS 优先使用 UDP 协议（速度快，无连接）。
2. 端口封装：
- 源端口：操作系统随机分配一个动态端口（如 54321），用于区分不同的应用请求。
- 目的端口：53（DNS 协议的知名端口）。
3. 数据单元：将 DNS 报文封装成 UDP 数据报。
 
 
 
第三层：网络层（Network Layer）
 
动作：添加 IP 地址，实现跨网路由
 
1. IP 封装：
- 源 IP：你的主机 IP（192.168.1.100）。
- 目的 IP：DNS 服务器 IP（223.5.5.5）。
2. 路由选择：系统判断 223.5.5.5 不在本地局域网，需将数据包发往 默认网关（如 192.168.1.1）。
3. 数据单元：将 UDP 数据报封装成 IP 数据包。
4. 关键问题：IP 包知道要发给网关，但数据链路层需要网关的 MAC 地址。
 
 
 
第四层：数据链路层（Data Link Layer）
 
动作：添加 MAC 地址，实现局域网传输（核心！）
这里会触发你刚学的 ARP 协议：
 
1. ARP 查询：主机发送 ARP 请求帧（广播），询问“192.168.1.1（网关）的 MAC 地址是什么？”。
2. ARP 响应：网关回复 ARP 响应帧（单播），告知其 MAC 地址（如  AA:BB:CC:11:22:33 ）。
3. 帧封装：
- 源 MAC：你的网卡 MAC 地址。
- 目的 MAC：网关的 MAC 地址（ AA:BB:CC:11:22:33 ）。
- 类型字段： 0x0800 （表示上层是 IP 协议）。
4. 数据单元：将 IP 数据包封装成 以太网帧（Frame）。
 
 
 
第五层：物理层（Physical Layer）
 
动作：转为比特流，物理传输
 
1. 编码：将以太网帧的二进制数据（0 和 1）转换为电信号（网线）或光信号（光纤）。
2. 传输：信号通过网线发送到交换机，再转发到网关（路由器）。
 
 
 
反向过程：从 DNS 服务器回到客户端
 
网关收到帧后，会解封装并通过路由转发到公网，最终到达 223.5.5.5。DNS 服务器处理后，原路返回响应（包含百度的 IP，如 180.101.50.242）。
 
1. DNS 响应：服务器构造 DNS 响应报文，包含百度的 IP。
2. 传输层：UDP，源端口 53，目的端口 54321。
3. 网络层：IP，源 IP 223.5.5.5，目的 IP 192.168.1.100。
4. 链路层：服务器通过 ARP 找到其网关 MAC，封装成帧。
5. 物理层：信号传输回你的主机。

关键考点与易错点
 
1. DNS 用 UDP 还是 TCP？
- 普通查询（请求 IP）用 UDP 53（快）。
- 区域传输（主从服务器同步数据）用 TCP 53（可靠）。
2. MAC 地址的变化：
- 数据在局域网内传输时，源/目的 MAC 是主机与网关的 MAC。
- 数据经过路由器转发到外网时，MAC 地址会逐跳改变，但 IP 地址保持不变。
3. ARP 的作用范围：仅在同一局域网内有效。客户端只需要知道网关的 MAC，不需要知道百度服务器的 MAC。

7. 三种前后端部署架构方案
方案 1：前后端分离（纯静态部署）
• 核心思路：前端与后端完全分离，前端静态资源独立部署。
• 前端：将打包后的 dist 目录（包含 HTML/CSS/JS/ 静态资源）部署到 CDN、对象存储或 Nginx 静态目录。
• 后端：独立的后端服务器（如 Node.js、Java、Go 等），提供 API 接口（HTTP/80、HTTPS/443），同时开放数据库（MySQL:3306）和 SSH（22）等端口。
• 交互：前端通过 JS 异步请求后端 API，获取数据后渲染页面。
• 适用场景：SPA 单页应用、对首屏加载速度要求不高、追求前后端解耦的项目。
￼
方案 2：SSR 服务端渲染（Next.js 等框架）
• 核心思路：使用 Next.js 等框架，将页面渲染逻辑放在服务端完成，同时保留前后端分离的 API 层。
• Nginx 反向代理：作为入口，将请求分发到不同服务：
◦ 根路径 /：指向 SSR 服务器（Node.js、Edge、Serverless 等），负责服务端渲染页面。
◦ API 路径 /api：指向 Next.js 自带的轻量 API 服务或独立后端，处理数据请求。
• 后端资源：SSR 服务器和 API 服务共同依赖后端代码、缓存（Cache）和数据库。
• 适用场景：对 SEO 友好、首屏加载速度要求高的网站（如电商、内容站）。
￼
方案 3：前后端混合部署
• 核心思路：前端静态资源直接嵌入后端服务器，不做独立部署。
• 部署方式：将前端 dist 目录直接放入后端服务器的静态资源目录（如 Java 的 resources/static、Node.js 的 public 文件夹）。
• 访问流程：用户访问时，后端服务器直接返回前端页面和 API 数据，无需额外的静态资源服务。
• 适用场景：中小型项目、快速迭代、对运维复杂度要求低的场景。
